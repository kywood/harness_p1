# 프로젝트 분석 결과 — 2026-10-23
- 범위 및 보존: 현재 작업 트리 기준 분석이다. 기존 Gemini/Aider 개발 결과를 유지했고 소스·Gradle·Manifest·테스트 코드를 수정하지 않았다. 분석 전부터 앱 및 상위 저장소에 staged/unstaged 변경이 있었으며 이를 덮어쓰거나 커밋하지 않았다. 이번에 요청한 보고서 두 파일만 추가했다. 빌드 과정에서 생성물·캐시가 갱신되며 기기 테스트용 APK가 에뮬레이터에 설치된다.
- 구조: 단일 `:app` 모듈, Kotlin DSL 및 Version Catalog 사용. 운영 Kotlin 11개는 `MainActivity`(입력/로딩/버퍼링 UI), `ui/MainViewModel`(StateFlow·상태 전환), `ui/StreamUiState`(5개 상태), `engine/TorrentEngine`(libtorrent 세션·파일 선택·다운로드·piece 우선순위), `ui/VlcPlayerScreen`(현재 재생 화면), `ui/PlayerScreen`(연결되지 않은 ExoPlayer 화면), `engine/TorrentFileDataSource`(ExoPlayer용 읽기), `engine/TorrentStreamServer`(연결되지 않은 localhost HTTP 서버), `ui/theme` 3개로 구성된다. 리소스·Manifest·백업 규칙은 표준 앱 골격을 유지한다.
- 구현된 흐름: 마그넷 입력 → 공백 제거/빈 값 검사 → 45초 메타데이터 조회 → 파일 선택 → 캐시 디렉터리 다운로드 → 선택 파일 우선순위·순차 다운로드 → 헤더/꼬리 piece 준비 또는 진행률 3%에서 VLC 자동 재생. 속도·피어·진행률 표시, 재생/일시정지, ±10초·슬라이더 탐색, 컨트롤 자동 숨김, 화면 버튼 취소/뒤로가기, ViewModel 종료 시 세션 정리가 구현되어 있다. 이는 코드 구현 확인이며 실제 토렌트 E2E 성공을 의미하지 않는다.
- Gradle/의존성: Wrapper 9.5.0(SHA-256 지정), AGP 9.3.3, Compose 플러그인 Kotlin 2.2.10, Compose BOM 2026.02.01; compile/target SDK 37, min SDK 26, Java 소스/타깃 11, daemon JVM 요청 25. AGP 내장 Kotlin 경로를 사용하며 별도 kotlin-android 플러그인은 없다. libtorrent4j 및 arm64/arm/x86/x86_64 JNI는 실제 별칭 버전 `2.1.0-39`(versions의 `2.1.0.0` 항목은 미사용), LibVLC `3.6.0-eap5`, NanoHTTPD 2.3.1, Media3 1.5.1, Lifecycle 2.6.1, Activity Compose 1.8.0, Core KTX 1.10.1, JUnit 4.13.2, AndroidX JUnit 1.1.5, Espresso 3.5.1. 저장소는 Google/Maven Central/JitPack이고 release 최적화는 비활성이다. 신규 의존성 선언은 추가하지 않았다.
- 실행 결과: 첫 Wrapper 실행은 JAVA_HOME과 PATH의 Java 부재로 실패했다. PowerShell 현재 프로세스에 `$env:JAVA_HOME = 'C:\Program Files\Android\Android Studio\jbr'`(JBR 25.0.2)를 지정한 뒤 `.\gradlew.bat :app:assembleDebug :app:testDebugUnitTest --offline --console=plain` 성공(42 tasks: 8 executed, 34 up-to-date). APK는 `app/build/outputs/apk/debug/app-debug.apk`; 단위 테스트 4개 성공, 실패/오류/스킵 0이다. clean 빌드·release·lint는 실행하지 않았다.
- 기기 테스트 및 오류 원인: `emulator-5554` 연결 확인. `:app:connectedDebugAndroidTest --offline --console=plain`은 캐시에 UTP `android-test-plugin-host-additional-test-output:32.3.3`이 없어 실패했다. configuration cache 직렬화 오류는 이 의존성 해결 실패에 수반된 메시지다. 같은 명령에서 `--offline`을 빼고 재실행하자 의존성 해결 후 Medium_Phone API 37에서 1개 테스트가 성공했다(68 tasks: 31 executed). 확인된 초기 실패는 환경/캐시 문제이며 현재 Debug 소스 컴파일 오류는 재현되지 않았다.
- 확인된 논리 문제/미완성: TorrentEngine 파일 선택의 중첩 조건은 확장자와 무관하게 전체에서 가장 큰 파일을 선택한다. VLC는 로컬 파일을 직접 열어 piece 다운로드 여부를 확인하는 DataSource를 우회한다. 헤더/꼬리 두 piece 또는 전체 진행률 3%는 연속 재생 가능 구간을 보장하지 않는다. 탐색의 시간→바이트 비례 환산도 컨테이너/가변 비트레이트에서 부정확하다. ExoPlayer DataSource는 읽기 시작 piece만 검사하므로 경계 너머의 미완료 piece를 읽을 가능성이 있고, open 대기 시간 초과 후에도 읽기를 진행한다. HTTP 서버는 파일 길이만으로 준비를 판단하며 suffix/역방향/음수/다중 Range 처리가 불완전하다. 후자의 두 경로는 현재 UI에서 미사용이다.
- 수명주기·보안 검토: raw Thread를 작업 취소/세대 식별자로 관리하지 않아 메타데이터 조회 중 취소·재시작 시 이전 콜백이 상태를 바꾸거나 세션 필드가 경합할 가능성이 있다. stop은 선택 파일·통계 필드를 초기화하지 않으며 캐시 삭제/용량 정책이 없다. 시스템 뒤로가기·백그라운드 정책과 VLC EncounteredError/EndReached 이벤트 처리도 명시되지 않았다. 입력은 빈 값만 검사하고 magnet 스킴/infohash 검증·메타데이터 경로의 정규화 및 캐시 하위 제한이 없다. 앱 코드에서 링크의 디스크 저장은 발견하지 못했지만 FetchingMetadata에 원문 문자열을 보관한다. 영속 저장을 도입한다면 Android 보안 저장소가 필요하다. INTERNET/네트워크/Wi-Fi 권한, 앱 전체 cleartext 허용, 기본 백업 규칙과 allowBackup=true가 설정되어 있다.
- 검증 한계와 결론: 단위 테스트는 예제 덧셈 1개와 상태 데이터 생성 3개뿐이며, 기기 테스트 1개는 패키지명 확인이다. MagnetParser/TorrentDownloader라는 독립 컴포넌트, 엔진·ViewModel·읽기·취소 테스트 및 magnet→download→stream 통합 테스트는 없다. 실제 피어 연결·부분 다운로드 재생·탐색·JNI ABI별 실행은 검증하지 않았다. 현재 상태는 빌드·기본 테스트가 가능한 스트리밍 프로토타입이며, 기존 구조를 유지한 채 재생 안정성·취소 안전성·입력 검증과 기능 테스트를 우선 보강할 필요가 있다. 자동 개발은 시작하지 않고 분석 후 대기한다.
