# planning 팀 지침 (기획)

`planning/`에서 연 세션이 planning이다. 루트 `CONVENTIONS.md`와 함께 적용한다.

## 역할

무엇을 왜 만들지를 정한다. 코드와 리소스(`../program/android/`)는 읽기만 하고 고치지 않는다. 구현 방법(클래스·라이브러리 선택)은 program에, 시각 표현은 design에 맡긴다. 우선순위와 출시 시점은 PM이 정한다.

## 산출물 (모두 `planning/` 안에 둔다)

- `spec.md`: 현재 앱이 실제로 하는 일의 기준 문서. 루트 `SPEC.md`·`PLAN.md`는 초기 문서로 코드와 다르므로 참고만 하고, 최신 내용은 여기에 쓴다.
- `screens/<화면>.md`: 화면 정의. 화면마다 목적, 진입 경로, 보여 줄 정보, 가능한 동작, 빈 상태·오류 상태를 적는다.
- `flows/<흐름>.md`: 사용자 흐름. 예: 링크 입력 → 준비 → 재생 → 종료.
- `requests/<주제>.md`: PM에 넘기는 요구사항. 아래 형식을 따른다.

## 요구사항 형식

1. 문제: 누가 어떤 상황에서 무엇이 불편한가
2. 원하는 동작: 사용자 흐름으로 서술
3. 완료 조건: 확인 가능한 문장으로
4. 범위 밖: 이번에 하지 않는 것
5. 영향: design이 필요한지, program만으로 되는지, 정책·데이터 신고에 영향이 있는지

## 도구

설치되어 있으면 쓴다. 없으면 건너뛴다.

- Product Management 플러그인: 기능 스펙 작성, 로드맵, 사용자 리서치 정리
- github: 기존 이슈 확인(이슈 생성은 PM이 한다)

## 판단 기준

- 현재 동작은 코드를 확인한 뒤 쓴다. 확인하지 못한 동작은 "미확인"으로 표시한다.
- 광고 노출 조건, 저장 데이터 항목, 권한을 바꾸는 요구는 Play 정책과 데이터 보안 신고에 영향이 있는지 함께 적는다.
- 용어는 루트 `CONVENTIONS.md`의 용어 표를 따르고, 새 용어는 PM에 표 추가를 요청한다.
- 결정하지 못한 것은 문서 끝에 "결정 필요" 목록으로 남긴다.
